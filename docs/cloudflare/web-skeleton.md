# cf/web: the public site on Astro + Workers (SAKEM-075)

A local, thin slice of the new public site: **Astro 6 SSR on Cloudflare Workers** in front of the legacy Next app. It exists to prove the shape (SEO parity, redirects, pass-through, what runs in the Worker) before the remaining pages are ported. Context and decisions: [`README.md`](README.md).

**Status.** Built and tested locally only. Nothing is deployed, no Cloudflare account was used (`wrangler login`, `deploy` and every remote command were avoided; only `wrangler dev` in local mode and `wrangler deploy --dry-run`). **Visual QA was not done** (no browser was opened); layout, spacing and motion were not looked at, only HTML, CSS output and behaviour were checked.

## Run it

```bash
cd cf/web
pnpm install                    # its own lockfile; not a pnpm workspace
cp dev.vars.example .dev.vars   # fake local values, untracked
pnpm stub-origin                # terminal 1: stand-in for the legacy app, :4390
pnpm fixture-api                # terminal 2: content API with sample team, report and resource data, the blog from content/blog and the contact form, :4391
pnpm dev                        # terminal 3: astro dev on :4321 (the Worker runs in workerd)
```

| Command | What it does |
| --- | --- |
| `pnpm assets` | The asset pipeline (below): syncs a few root files, then makes the image ladders, the manifest and the PDFs from the root `public/`. Incremental. `dev`, `test` and `build` run it first |
| `pnpm build` | `pnpm assets`, then `dist/client` (assets) and `dist/server` (Worker), then `check-dist` (the asset guard) |
| `pnpm check:dist` | The guard alone, on an existing `dist/` (`-- --list` prints every `<img>` of the prerendered pages) |
| `pnpm check` | `astro check` (types for `.astro` and `.ts`); it only builds the image manifest, not the images |
| `pnpm test` | 1,956 unit tests in 55 files (vitest, `pnpm assets` first); the ones that read `dist/` (`built`, `home-built`, `home-dom`, `portal-enabled-built`, the dist audit in `assets`) need `pnpm build` first and are skipped without it |
| `pnpm test:e2e` | 541 checks against the built Worker under `wrangler dev` (local mode) with the stub origin (a stand-in for WordPress) and the fixture API |
| `pnpm test:e2e:portal` | The student portal switch in the prerendered pages: two more builds (the build variable, a decoy `.dev.vars`, an invalid value), five stacks; about three minutes (SAKEM-103) |
| `pnpm test:negative:phase-a` | 92 safeguards of Phase A (the switch, the navbar and its menu, the pass-through, the registration link, the uploads, HSTS, and the move of the reports into /donasi), each broken in turn: the tests must fail (SAKEM-103, SAKEM-106, SAKEM-105) |
| `pnpm measure [-- --next http://127.0.0.1:3055]` | Sizes, warm timings, and the "does the Worker run?" experiment; writes `.measure/results.json` |
| `pnpm exec wrangler deploy --dry-run --outdir <dir> -c dist/server/wrangler.json` | Bundle size, no login needed |

`BLOG_SOURCE=markdown pnpm dev` runs the blog from the root `content/blog` rendered at build time instead of the content API (no fixture server needed; see "Blog from the content API"). `E2E_PORT_OFFSET=1000 pnpm test:e2e` shifts every port the e2e stack uses, so two sessions can run it on one machine.

`astro dev` differs from production in two ways: static assets are not served before the Worker, and `_redirects` is not processed (the middleware answers the same redirect table instead). Use the built Worker (`pnpm test:e2e`, or `wrangler dev -c dist/server/wrangler.json`) to see production behaviour.

## Decisions and why

- **Design tokens are copied, not imported.** `src/styles/global.css` holds the `:root` vars, the `@theme inline` block, the base heading scale, the focus ring and `.blog-content` from `app/globals.css`. Importing the root file by path would pull in its Leaflet styles and, worse, its `@source not "../cf"` (added in commit 1), which would stop Tailwind from scanning this app's own files. `tests/tokens.test.ts` fails if a value drifts from the root file.
- **Fonts** are self-hosted with `@fontsource` (static files, Lora 400-700 and Plus Jakarta Sans 400-700, latin only, like `lib/fonts.ts`); two are preloaded. No Google Fonts request.
- **Blog content at build time: a small Vite plugin** (`plugins/blog-content.mjs`) turns `content/blog/*.md` into two virtual modules: a metadata index (read by the prerendered home page for its "Cerita & Inspirasi" strip, and by the markdown fixture) and the rendered bodies (imported only by the markdown fixture, so no article text is in a production Worker bundle; a test checks this). Since SAKEM-080 part E the articles themselves are not built from it: the pages read the content API ("Blog from the content API" below), and this plugin is the home strip, the `BLOG_SOURCE=markdown` fixture and, through `createBlogReader`, what `scripts/fixture-api.mjs` serves. The markdown is rendered with the engine react-markdown uses (remark-parse, remark-gfm, remark-rehype), the same `img` and `a` handling, and the plugin looks every image up in the asset manifest to put `srcset`, `sizes`, `width` and `height` on every `<img>`. Why not `import.meta.glob('?raw')` or `astro:content`: parsing and rendering happen once in Node, so the Worker and the workerd prerender never see a file system, and no raw markdown or parser ships in the Worker.
- **Redirects: one table, compiled to `_redirects`** (`redirects.config.mjs`). The assets layer answers `_redirects` before the Worker runs, so legacy WordPress traffic costs no Worker request and no CPU. Astro's own `redirects` option was not used: with params the adapter's generator (`@astrojs/underscore-redirects` 1.0.3) writes `/cerita/:slug  /cerita/:slug.html  301` and drops the destination and the status. The same table feeds the middleware (used by `astro dev` and as a safety net) and the tests, so there is one source.
- **Pass-through in a middleware plus a catch-all route.** Astro middleware only runs for a request that matches a route; without a catch-all (`src/pages/[...path].astro`) an unmatched multi-segment path such as `/portal/status` gets Astro's built-in 404 and never reaches the middleware (found in the first e2e run). The catch-all also resolves shortlinks (below), through the API.
- **`security.checkOrigin` is off.** Astro's origin check answers 403 to any POST/PUT/PATCH/DELETE with a form content type and no matching `Origin`, which would reject requests the legacy app accepts (server-to-server callbacks, a form posted from the LMS host). The Astro pages here have no state-changing endpoint; the contact form, when ported, validates `Origin` itself.
- **The 404 is SSR, not prerendered.** A prerendered `404.html` is a static file and the assets layer serves static files with status 200 (`/404` itself answered 200 in the first build). Cost: one small render per unknown URL.
- **One URL per page.** The middleware folds a trailing slash and `.html` with a 308 (Next does the same for the slash); the page's canonical link is the second line of defence. A prerendered page requested with a trailing slash is redirected by the assets layer with a **307**, not Next's 308 (not configurable).
- **Images.** Plain `<img>` with `width`/`height`, `srcset` and `sizes`; `loading="lazy"` except the hero photo (`loading="eager" fetchpriority="high"`). No Cloudflare Images and no runtime transform: every image is made at build time and served as a static asset. How: [Images and other static assets](#images-and-other-static-assets).
- **Program galleries** (`src/lib/gallery.ts`, SAKEM-080). The legacy `lib/gallery.ts` lists `public/images/program/galeri/<program-id>/` with `readdir` on every request, which a Worker cannot do (no file system; it would fail silently into an empty gallery). `getProgramGallery(id)` now reads the asset pipeline's manifest (`listImages`, see "Images and other static assets"): the pipeline reads the same folders at the repo root, so adding a photo is still "drop `4.jpg` in the folder, rebuild". Each photo gets the WebP ladder (480 to 1600 px, never enlarged, EXIF orientation applied) at hashed `/_img/<hash>-<width>.webp` URLs, so replacing a photo in place changes its URL (what the `?v=` suffix did on the Next app) and the files are cached as `immutable`; a derivative nothing refers to any more is deleted on the next run. The listing rules are the legacy ones: numbered files first in numeric order, then other names alphabetically; jpg, jpeg, png and webp (an avif or gif among the images **fails the build** instead of being skipped). A folder without photos, or no folder, **hides the whole "Galeri Foto" section** (no "coming soon" box). A photo sharp cannot read fails the build and names the file. **Alt text rule** (same as the legacy page): `Dokumentasi <program title> <position>`, with the position counting from 1 in display order, not the number in the file name. The images are plain `<img>` with `width`, `height`, `srcset`, `sizes` and `loading="lazy"` (the stage photo above them is the page's LCP image). This began as its own script (`build-gallery.mjs`, 480 and 960 px) and was folded into the pipeline once it existed, as that script's notes planned: one encoder, one manifest, one hash scheme, one set of headers.
- **Program photos and the share image.** The stage photo and the four activity thumbnails are imported by the page, so Astro hashes and resizes them (`astro:assets`), not the asset pipeline; moving them to `<Img>` is a follow-up (the share image would become the optimized original URL). The share image (`og:image`, `twitter:image`) is the stage photo as a 1200 px JPEG made at build time; the Next layout used the original file (up to 2.6 MB), so the URL differs but still names the same photo.
- **Security headers** that Caddy adds today (HSTS, nosniff, X-Frame-Options, Referrer-Policy, Permissions-Policy) are re-added for Worker and asset responses (`public/_headers` and the middleware); a test keeps them equal to the Caddyfile **except HSTS, which is staged on purpose** since SAKEM-103: `max-age=300` with no `includeSubDomains` and no `preload`, raised in steps after the cutover ([HSTS in steps](#hsts-in-steps-f-01-d-04-p-19)). Answers of the origin (the pass-through) are not given any of these headers: they carry what WordPress sends.
- **Team API contract** (`src/lib/team-types.ts`): `GET /api/public/team` (through the binding, or `${CONTENT_API_URL}` locally) returns `{ "members": TeamMember[] }` shaped like the `team_members` row of `lib/db/schema/team-members.ts` (dates as ISO strings); a bare array is accepted. **This endpoint does not exist in the legacy app yet.** Cache: 5 min fresh, 7 days stale; on failure the stale copy is also re-served as fresh for 30 s so an outage costs one 2 s wait per 30 s, not one per request. `TEAM_CACHE_FRESH_SECONDS` tunes the fresh window.
- **Content lists: one loader (SAKEM-080 part D).** `src/lib/content-api.ts` is the only implementation of the timeout, `caches.default` and stale-if-error. `/tim` (`lib/team.ts`), the reports of `/donasi` (`lib/reports.ts`, with `loadReportsSection`: it never throws) and `/gabung-siswa/docs` (`lib/resources.ts`) each add their path, their parser and nothing else. The payloads are the contract's (`content-api.md`), parsed tolerantly: a malformed entry is dropped, a payload that is not a list is an API failure. The grouping is the root app's: `getReportsByYear` (newest year first, compared as strings, the API's order inside a year) and `getResourcesByCategory` (the five categories in their fixed order, empty ones omitted).
  - **Cache.** Fresh window **60 s** for reports and resources (the contract's `s-maxage`; `CONTENT_CACHE_FRESH_SECONDS` tunes it, the e2e uses 1 to 2 s), stale copy kept 7 days, a failed fetch re-serves the stale copy for 30 s. `/tim` keeps its 5 minutes for now (moving it to 60 s is the one constant `TEAM_FRESH_SECONDS`).
  - **Purge on admin save.** The cache keys are synthetic URLs made of the API's base and the path: `<base>/api/public/reports` and `/resources` (fresh), and the same with `?copy=stale`, where `<base>` is `CONTENT_API_URL` locally and `https://api.internal` (the placeholder host of the service binding) in production. A purge deletes the fresh key from the Astro Worker's `caches.default` and the next request refetches; the stale key is only read after a failed fetch and is overwritten by the next good answer. The Cache API is per data center, so a purge from another Worker reaches one location only; how the admin reaches all of them (for example a zone purge of the page URL) is not settled here.
  - **Page headers** (`contentPageHeaders`). Fresh data: `public, max-age=0, s-maxage=60, stale-while-revalidate=300` (the contract's value; `max-age=0` so a browser never holds a copy past a save). Stale data: `s-maxage=30`. **Nothing to show** (API down on a cold cache, or neither the binding nor `CONTENT_API_URL` configured): a **503 with `Retry-After: 30` and `no-store`**, the full page shell and a notice, so a crawler keeps what it has instead of indexing an empty list. An **empty list** is the legacy empty state, a normal 200. The two notices (`Laporan belum dapat ditampilkan`, `Dokumen belum dapat ditampilkan`) are **new copy**: the legacy pages had no such state (a database error was a 500), so they are for Dzul to review. `/tim` still answers 200 with its empty state in that case.
  - **Files.** The API's `filePath` is the link target as it is, root-relative or an absolute `https` URL; the Worker never proxies uploads. The parser refuses anything else (`javascript:`, `//host`, a backslash, control characters), and an external link of a resource must be `http(s)`. Until uploads are served from R2 these paths still reach the pass-through (`/reports` and `/resources` are in `LEGACY_PATHS`).
  - **Copy buttons.** A text snippet is a `<pre>` and a button (`data-copy-text` names the `<pre>`'s id; `aria-label` "Salin teks <title>"). The button ships `hidden` and the script un-hides it, so without JS there is no dead button (its row keeps the button's height, so un-hiding shifts nothing). The label swaps to "Tersalin" for 1.8 s (the legacy wording and timing), a visually hidden `role="status"` says so ("Teks tersalin ke papan klip."), and a refused clipboard falls back to a hidden textarea and `execCommand` (an `astro check` hint about its deprecation, like `/donasi`).
  - **Design system additions.** The report categories use the legacy Tag hues (`blue`, `green`, `purple`, `amber`, plus `red` and `gray`), added to `lib/ui.ts` with the root class strings, and eight lucide icons went into `Icon.astro` (`book-open`, `clipboard-list`, `folder-open`, `sparkles`, `users`, `external-link`, `link`, `type`).
  - **"Open Recruitment Gen 6"** is hard-coded as in the legacy page, with a comment pointing at SAKEM-059.

- **Blog from the content API (SAKEM-080 part E).** `src/lib/blog.ts` hands the pages a `BlogSource` (`list`, `article`, `all`); two implementations sit behind it. **`api`** (default, what production runs) is `src/lib/blog-source.ts`: `GET /api/public/blog?page=&pageSize=` and `/blog/{slug}` of [`content-api.md`](content-api.md) through the **same loader as the other content lists** (`src/lib/content-api.ts`: `caches.default`, **60 s fresh** with `CONTENT_CACHE_FRESH_SECONDS`, a 2 s timeout, the last good copy for 7 days, **stale-if-error**, re-served as fresh for 30 s during an outage so it costs one 2 s wait per 30 s). The blog needed three additions, all optional on `loadContent` and off for the other callers: `notFoundTtlSeconds` makes the contract's `404 {"error":"not_found"}` an answer (source `not_found`, remembered for 30 s so probing cannot hammer the API, and the stale copy is dropped so an outage after an unpublish cannot bring the article back; a 404 with any other body, such as a wrong base URL answering HTML, stays a failure, so it can never make a page look deleted); `serialize` stores the parsed value, so `contentMarkdown` (unused here, half of the payload) is not cached or parsed again; `onFailure` logs a fixed word (`status 500`, `timeout`, `invalid payload`), never a body or a URL. The page answers by what the loader returned, through `contentPageHeaders` like `/gabung-siswa/docs`: 200 with `s-maxage=60` (fresh) or `s-maxage=30` (stale), **404** with `s-maxage=30` for `not_found`, **503** with `no-store` and `Retry-After: 30` when there is nothing to show; `x-blog-source: network|cache|stale|empty|not_found` for debugging. **`markdown`** (`BLOG_SOURCE=markdown`, read by `astro.config.mjs` and `vitest.config.ts` as the build-time constant `__BLOG_SOURCE__`) is the old behaviour, `src/lib/blog-markdown.ts` over `virtual:blog-index` and `virtual:blog-bodies`: a fixture for `pnpm dev` without the fixture API and for tests, never for a deploy. It is reached through a dynamic import behind the constant, so a production build holds no article text (`tests/built.test.ts` checks the bundle: no body and no slug of the markdown index). The pages cannot tell them apart. One implementation of the contract's rules (`featured`, paging and clamping, `pageSize` 1 to 50, `related`, the slug grammar, the page cap) is `blog-contract.mjs`, shared by the markdown adapter, the fixture API (`scripts/fixture-api.mjs`, which serves all 80 articles from `content/blog` through the same render pipeline as the build, `createBlogReader` in `plugins/blog-content.mjs`) and the tests; the old sync helpers (`getRelated`, `getBlogPage`) are thin wrappers over it. The page shows `contentHtml` **unescaped** (`set:html`): trusted only because the API sanitizes at save. Covers are looked up in the asset manifest at request time (`coverAttrs`): a migrated image gets its WebP `srcset` and the `%40` form, the width and height are the API's (`imageWidth`, `imageHeight`), any other path (an R2 upload, an external URL) is used as given. **Inline images inside `contentHtml` are used as given**: the markdown fixture's HTML has `srcset`, `width` and `height` from the manifest because the build pipeline rendered it; HTML the API's save-time renderer produces has what that renderer puts there (the seed of the 80 migrated articles should be rendered with `plugins/blog-content.mjs` to keep their responsive images). A slug outside `^[a-z0-9][a-z0-9_-]{0,199}$` is a 404 without asking the API; `?page=` is capped at 500 before it is asked (so probing creates a bounded number of cache keys). Nothing in front of the Worker honours `s-maxage` today (the Worker runs before the zone cache); the header is the contract's value for anything that does later. **Do not turn on Workers Cache (`cache.enabled`) to speed this up: its docs bill every request, static assets included, as a Worker request, which would spend the 100k a day on images.** The sitemap is SSR too (`all()`: page 1 with `pageSize=50`, then the rest, plus `featured`, sorted newest first); with the API down and no copy it answers 503 with `Retry-After: 300` instead of a sitemap without the articles. Its `lastmod` is `modifiedISO` when a list entry carries it (the contract's entries do not), else the publication date `dateISO`; the markdown sitemap used `modifiedISO`, so an edited article may show its first date until the API adds `modifiedISO` to list entries (a backwards compatible change, parsed already). The blog reaches the API through `lib/api-client.ts`: `CONTENT_API_URL` when set (local, CI), else the `API` service binding; since the binding PR so do `/tim`, `/donasi` (then `/laporan`) and `/gabung-siswa/docs` (see "Service binding and Turnstile"), so no page needs a public API URL in production. The home page's "Cerita & Inspirasi" strip still reads the build-time markdown index (the home page stays prerendered and costs no Worker request): a new article shows there after the next build, not at once.

This Worker refuses nothing for lack of a token (that would break the no-JavaScript path wherever the API has no secret).
  - **A refusal.** `400 turnstile_failed` is its own outcome: the page answers **400**, `no-store`, the banner **"Verifikasi gagal. Silakan coba lagi."** (new copy, the site's own words, not the API's), the typed text kept and the form rendered again, which **is** the widget's reset: a new widget and a new token (the spent one is not echoed). Not logged (it is the visitor's, or a bot's, outcome). Any other 400 or 5xx stays "unavailable" as before.

The honest trade-off: **in production a visitor without JavaScript cannot send a message** (the API has a secret, so a post without a token is `turnstile_failed`); wherever the API has no secret (local runs, tests, e2e, CI) the check is skipped and the plain POST still works, which is what lets the tests post without a browser. The server side stays fail-closed in production: no secret, an unreachable Siteverify or a missing rate-limit binding is a 500 on the API that stores nothing (shown here as "unavailable", 503).

## Images and other static assets

Every image and file is a **static asset** (free and unlimited; anything that goes through the Worker counts against 100k requests per day). The root `public/` is the single source and is never modified; everything below is generated into gitignored folders of `cf/web` by `scripts/build-assets.mjs`, which `pnpm dev`, `pnpm test` and `pnpm build` run first. Numbers and settings live in `assets.config.mjs` (pure, shared by the script, the blog plugin, `src/lib/images.ts` and the guards).

**What it makes, for every `jpg`, `jpeg`, `png` and `webp` under `public/images/**` and `public/blog/images/**` (288 files: 249 blog images and 39 site images, counted on 2026-10-15):**

| Output | Path | What |
| --- | --- | --- |
| WebP ladder | `public/_img/<hash>-<width>.webp` | 480 / 768 / 1200 / 1600 px wide, never upscaled; a rung within 10% of the top one is skipped, the top is the source width capped at 1600; quality 80; PNG sources take a lossless WebP when it is at most 1.5x the lossy one (logos, screenshots, infographics, the QRIS); metadata dropped; EXIF rotation applied. 614 files for 273 images (identical sources share their derivatives) |
| Original URL | `public/<same path>` | An optimized file **in the format the extension says**, at most 1600 px wide, metadata (EXIF, GPS) stripped: JPEG mozjpeg q82; PNG lossless, palette-quantized only when it is still above 1 MiB; so `/blog/images/2025/10/1.png`, `/wp-content/uploads/...` redirects, old links and `og:image` keep working. A few migrated files are PNG data named `.jpg` (two testimonial photos) or WebP named `.png` (one partner logo): they are served as what the extension says |
| Manifest | `src/generated/image-manifest.json` | `{ "<url path>": { width, height, hash, variants: [{ width, height }] } }`, typed by `src/lib/images.ts` (`findImage`, `getImage`, `imgAttrs`, `listImages` for gallery folders). `width`/`height` are the size of the file at the original URL (the largest rung) |
| Files | `public/files/**` | Copied; a PDF above 20 MiB is recompressed (next section) |

**File names.** `<hash>` is 12 hex characters of SHA-256 over the source bytes, the encoder settings and `PIPELINE_VERSION`, so a name changes if and only if the bytes it points at change: that is what makes `max-age=31536000, immutable` safe. The same content under two paths shares one derivative. Original URLs cannot carry a hash (they must stay), so they get a day of cache instead.

**Incremental.** The manifest is a pure function of the sources and is rewritten only when it changes. A derivative is skipped when its file exists (the name is the hash); an original-URL file when `.asset-state.json` (gitignored) holds the same hash and format for it; files are written to a temp name and renamed, so a killed run never leaves a half file that looks fresh; stale files in the generated folders are removed. **Change an encoder setting in `assets.config.mjs` and bump `PIPELINE_VERSION`** so every hash changes. Cold run on this machine: 36 s for everything (full `pnpm build` 42 s); warm: 0.1 s (full `pnpm build` about 5.5 s).

**Using an image.**

1. Put the file in the root `public/images/...` (site) or `public/blog/images/...` (blog), like before; the URL path is the path below `public/`.
2. `pnpm assets` (or just `pnpm dev` / `pnpm build`).
3. In a component: `<Img src="/images/program/mentoring.jpg" alt="..." sizes="(min-width: 1024px) 380px, 100vw" />` (`src/components/Img.astro`: plain `<img>` with `src`, `srcset`, `sizes`, `width`, `height`, lazy by default; the LCP image passes `loading="eager" fetchpriority="high"`). An unknown path **fails the build**. `sizes` is the layout width of the image: the 1200 px page container is 1152 px of content, 800 px for reading width; check the real grid (`(min-width: 1024px) 380px` is the three program cards).
4. In a blog article nothing changes: `![](/blog/images/...)` in the markdown gets `srcset`, `sizes`, `width` and `height` from the same manifest; covers carry `imageSrcset` in the metadata.
5. Budgets: keep each source reasonable (the pipeline caps at 1600 px and every generated image is asserted under 1 MiB), do not add thousands of files (the Workers limit is 20,000 per version; the build fails above 10,000), and avoid characters other than letters, digits, `/ . _ -` in names: a literal `@` (five existing blog images) is answered by the assets layer with a **307** to the `%40` form, so markup carries `%40` (`assetUrl`) and the guard flags a literal `@`; the tests fail on any other character.

**Other image paths in the tree today.** A few components still import an image (`import photo from '@root/public/...'`), which makes Astro hash and resize it into `/_astro/` (`astro:assets`): the logos in the navbar and footer, the partner logos and testimonial portraits of the home page, the program page's stage and activity photos, and the QRIS on `/donasi`. They work and are not wrong; the QRIS stays an import on purpose, because its download link must be the original bytes. Everything new should use `<Img>` or the manifest so there is one system; moving those over is a follow-up (each touches a page or component of its own and its tests).

## Pass-through

How it works: the middleware (`src/middleware.ts`) checks the redirect table, then answers `/admin` (a 308 to the admin host) and `/api` (a JSON 404), then asks `src/lib/legacy-paths.ts`, and forwards with `src/lib/legacy-proxy.ts`. **Since SAKEM-103 (Phase A of the cutover) the origin behind the route is the live WordPress site, and what is forwarded is WordPress's own paths and nothing else**: `/wp-admin/*`, `/wp-login.php`, `/wp-content/*`, `/wp-includes/*`, `/wp-json/*`, `/xmlrpc.php` and `/login`. (Before it the list held the legacy Next app's static prefixes, `/_next`, `/images`, `/blog/images`, `/files`, `/reports` and `/resources`. That app was never released and the VPS is gone: team photos, reports and documents come from R2, which is finding F-10 of the cutover runbook, so none of those prefixes is forwarded any more and an address with no file is the site's 404.) The request goes out with its method, headers (cookies and `Authorization` included), query and body stream; **redirects are not followed** (a 302 from WordPress reaches the browser); hop-by-hop headers are dropped; several `Set-Cookie` headers survive as several. The answer is **the origin's, untouched**: the Worker adds no security header to it (so a WordPress screen that frames itself keeps working, and WordPress's own HSTS, if it sends one, is what the browser sees). In production (Workers **routes** mode, one route covering the whole site, in front of the proxied WordPress record) `fetch()` of the same URL reaches WordPress behind the same hostname, so `LEGACY_ORIGIN_URL` stays unset (the variable keeps its name although the origin is WordPress now). Locally it points at `scripts/stub-origin.mjs`, a stand-in that answers like WordPress (a sign-in form with cookies, a 302 from `/login` and `/wp-admin/`, an XML-RPC 405, uploads, a JSON echo) and records what it received. On staging, which has no origin behind its hostname, the deploy command passes a `*.invalid` host, so a forward **fails at once** instead of looping back into the Worker.

**Strict, in both directions.** Entries are matched on a path-segment boundary, case-sensitively; `/wp-login.php`, `/xmlrpc.php` and `/login` are `exact` entries (themselves, with or without ONE trailing slash, nothing below them). `/wp-adminx`, `/wp-admin-old/x`, `/wp-contentx/a.css`, `/wp-login`, `/wp-login.php.bak`, `/xmlrpc`, `/login/x`, `/login-help`, `/Login`, `/WP-ADMIN` and `//wp-admin` only look like WordPress: they are the Worker's (its 404 page, or, for a single slug-shaped name, a shortlink lookup, which is skipped for every reserved name, so another spelling such as `/WP-ADMIN` or `/Login` costs no D1 read). The other direction matters as much: **nothing the new site serves is ever on the list** (`tests/legacy.test.ts` builds the site's pages, program ids, redirect sources, shortlink names and portal names and checks that none is forwarded), and **no redirect rule may sit on a forwarded path**, because the redirect table is answered first (by the assets layer, before the Worker) and WordPress would never see the path. That is why the table lost `/login` and the four other auth names, `/daftar` and the splat over `/wp-content/uploads` (below).

**WordPress uploads (F-05 of the runbook).** The splat `/wp-content/uploads/*` to `/blog/images/*` is gone. It sent every upload to a `/blog/images` address, which is a 404 for all but the 249 files the 86 articles use. Now `_redirects` carries **one rule per file this build ships under `/blog/images`** (`mirroredUploadRules` in `redirects.config.mjs`, written by the build from the file list of `dist/client`, like the trailing-slash folds): a 308 to the copy, answered by the assets layer with no Worker request, so the most requested images stay free. A name with an `@` (five photos) is written in its `%40` form, so it is one hop, not the 308 plus the assets layer's own 307 it took before (the parity rehearsal's one `redirect-chain` and `redirect-temporary` warning are gone with it). Every other upload, and anything else under `/wp-content`, is WordPress's and is forwarded. 249 static rules of the 2,000 allowed (249 files today; the tests check the file stays inside the limits with a thousand).

**Proven locally** (e2e, group `pass-through`, against the stand-in): GET/POST/PUT/PATCH/DELETE/HEAD reach it with method, query, body (also a 1 MB body), custom headers and cookies intact; a POST sign-in's two `Set-Cookie` and a form's two arrive as two; the origin's 302 is not followed and its absolute `Location` points back at the host the browser used; `te` and `proxy-authorization` are not forwarded; the origin's `Cache-Control` survives and the Worker adds no header of its own; a trailing slash is the origin's business (`/login/` is not folded with a 308); each of the 14 WordPress paths of the list reaches it once, with the same path and query; 21 look-alikes never do; and **a sweep of every page, redirect, shortlink, the admin and API names, the portal names and the old Next paths of the new site never reaches it**. **Not provable locally:** route-mode semantics (below).

### The student portal switch

`PORTAL_ENABLED` (SAKEM-103) decides whether a page offers the student portal: the navbar's **"Masuk" link and its session script** (`GET /portal/api/auth/get-session`). **Default OFF**: Phase A runs with it unset, and a page then has neither the link nor the script nor even the address `/portal/api/auth/get-session` (a test scans every prerendered page and the built Worker's answers for it). It is a **public** variable (it only decides what is in the HTML), read exactly like the Web Analytics beacon, because the site has the same two kinds of page:

| | Pages | Where the value comes from | How it is set |
| --- | --- | --- | --- |
| **Build** variable | the **prerendered** pages: `/`, `/gabung-siswa`, `/program/<id>` (5 files, served by the assets layer; `/donasi` was the sixth until SAKEM-105 made it a Worker page) | the **shell environment of `astro build`**, read by `astro.config.mjs` into the constant `__PORTAL_ENABLED__` | `PORTAL_ENABLED=true pnpm build`, on the command line (not `export`ed: a later staging build in the same shell would take it) |
| **Worker** variable | the pages the **Worker renders**: the blog, `/tim`, `/donasi`, `/gabung-siswa/docs`, `/kontak`, the 404 page, the polite `/daftar` page | `env.PORTAL_ENABLED` at request time | `--var PORTAL_ENABLED:true` at deploy (public per-deploy values are never in git; the staging printer accepts it for the site only) |

Each kind reads **only its own source, no fallback either way** (`portalEnabled` in `src/lib/portal-enabled.ts`): a deploy has to set both, from one decision, or half the pages disagree (the runbook's smoke test T-35 compares a prerendered page with a rendered one). The prerender's own `env` holds `.dev.vars`, a local-development file, and must never decide what static HTML says, so a prerendered page reads the build constant only (`scripts/e2e-portal.mjs` builds with a decoy `.dev.vars` on both sides to prove it).

**Strictly validated:** exactly `true` turns it on (surrounding whitespace ignored); unset, empty or exactly `false` is off and silent; **anything else** (`TRUE`, `1`, `yes`, a JSON boolean that reached the Worker as a var, text around the word) is off, and the Worker says so **once per isolate, in fixed words, without the value** (`portal: PORTAL_ENABLED is set but is neither "true" nor "false"; the page is rendered with the portal off`; the build prints the same once). The value is never echoed in a page or a log.

**The navbar while it is off: the slot is EMPTY** (decided by Dzul, 2026-10-15). The mobile bar and the mobile menu do not change; nothing is added to the text of the page. The footer is unchanged, and registration is reached from the pages' own "Daftar Sekarang" buttons (the home page's student card, both buttons of `/gabung-siswa`, the link of its documents page). While the switch is on, "Masuk" is back, with its wrapper, the menu is back in the centre column (its `<ul>` has neither of the two classes: the page is as it was before SAKEM-106), and the session script (`src/components/NavbarSession.astro`) is rendered **by the navbar only then**, right after the navbar's own script. The reserved shortlink name `laporan` stays reserved (the path is the redirect's).
- **The sitemap** loses `/laporan` (a redirect is not a sitemap URL) and keeps `/donasi`. The SEO parity tool lists `/laporan/` among the redirects of the table and reads it as one 308 to a page that exists (an INFO finding, no blocker); its local rehearsal checks that.
- **Checked by:** `tests/public-pages.test.ts` (the one address, `/donasi#laporan`, in the section's id, the footer, the table), `tests/copy.test.ts`, `tests/redirects.test.ts` (rules, query before the fragment, no chain), `tests/reports.test.ts`, `tests/page-cache.test.ts`, `tests/built.test.ts` (`_redirects`), the e2e groups `donasi`, `reports`, `degraded`, `stale`, `page-cache`, `redirects`, `canonical-url`, the production checker's T-37 and T-05, and the negative checks of `phase-a`, `page-cache` and `production`.

### HSTS in steps (F-01, D-04, P-19)

The VPS Caddyfile's `Strict-Transport-Security: max-age=31536000; includeSubDomains; preload` would commit every subdomain of the domain (the hosting's webmail and cPanel included) to HTTPS for a year in each browser that has seen it, and would make a rollback to anything without a valid certificate for the apex impossible. So the Worker and the assets now send **`max-age=300`, with no `includeSubDomains` and no `preload`** (`src/lib/security-headers.ts` and `public/_headers`, kept equal by `tests/headers-sitemap.test.ts`, which also pins that neither carries `includeSubDomains`, `preload` or a year). The Caddyfile is the legacy stack's and is never served by the Worker; the test lists HSTS as the one deliberate difference. Pass-through answers carry the origin's own header, untouched.

It is **raised in steps after the cutover** (X-07 of the runbook, once the first week was quiet): the proposal is one day, then one week, then 30 days; `includeSubDomains` only after every subdomain of the zone has been checked for HTTPS; `preload` last, and only on purpose (submitting the domain is not undoable in a hurry). Each step is one string in two files, with the test, in one pull request.

### Conflicts and findings

- **Shortlinks.** `sakolakembara.org/<slug>` was resolved by Next's root `[slug]` route against Postgres, and the catch-all forwarded a single segment that fits the slug grammar to the legacy origin. **Since SAKEM-082 the catch-all resolves it itself**: the same grammar (same regex and 64-character limit as `validateSlug`) decides whether it is a candidate, then one call through the `API` binding (`GET /api/public/shortlinks/<slug>`, lower-cased) answers a `307` to the target, the site's 404 (unknown or inactive; a page of its own for `/daftar`), or a plain `503` when the API cannot answer; anything that cannot be a slug is a 404 from the Worker without a call. The lookup is never cached (a hit would not reach the API, which counts the click), and the origin is not asked. Static pages, forwarded paths and redirect rules still win over the catch-all, like in Next, which is why the admin refuses to create a link with the name of one ([`admin-konten.md`](admin-konten.md#5-shortlink)).
- **Files both sides serve.** The Worker ships copies of `favicon.ico`, `icon.png`, `apple-icon.png`, `og-default.jpg` and `images/logo-sakola-kembara.png` (copied from the root at build time, gitignored, so the root stays the single source). The assets layer answers first. `/robots.txt`, `/sitemap.xml`, `/blog`, `/blog/<slug>`, `/program/<id>` and `/donasi` are Astro's now, and WordPress's versions of them (WordPress has its own `robots.txt` and sitemaps) are unreachable once the route is attached. Every image and PDF in the repo (blog, program galleries, hero, partners, QRIS...) is served from the assets layer too (see "Images and other static assets").
- **Every pass-through is a Worker request** (100k per day on Free, shared by every Worker of the account), and in Phase A **WordPress is probed all the time**: `/wp-login.php`, `/xmlrpc.php`, `/wp-admin/...` and `/wp-json/...` now reach the Worker and then the origin (they used to be a 404 render). The runbook's F-09 is updated: a WAF rule must **not** block `/wp-login.php`, `/wp-admin` or `/wp-json` while they are WordPress's admin; see there. The e2e checks that no image or PDF request reaches the origin, and a `/blog` list view still costs one Worker request.
- **Blog content source of truth.** *Settled by SAKEM-080 part E:* the blog is managed in the new admin (D1, HTML rendered at save time) and the site reads it from the content API at request time. `content/blog/*.md` stays the seed of the 80 migrated articles and the markdown fixture; the WordPress posts a visitor can still open at `/wp-admin` are not read by anything here.
- **Client IP.** The contact form reads `CF-Connecting-IP` itself and passes it to the API Worker in `X-Sakem-Client-Ip` over the service binding (see "Contact form"). For a forwarded request, whether Cloudflare keeps that header on a Worker's subrequest to the origin (WordPress logs, a security plugin that rate-limits sign-ins by address) needs a check on a real zone.
- **Sign-in cookies and nonces.** A WordPress sign-in sets several cookies and redirects; the proxy keeps every `Set-Cookie` and does not follow the redirect (proven against the stand-in), but whether WordPress, behind a Worker route, still builds its absolute addresses from the right host (`siteurl`, the proxy headers, `https`) is a real-zone fact: runbook T-31 to T-34.
- `/blog/page/N?utm=x` loses the incoming query (`_redirects` keeps the destination's own query only). Not worth a code path.

## Web Analytics (SAKEM-095, decision D-07)

**Decision (Dzul, 2026-10-15, D-07):** visitor analytics of the new site is **Cloudflare Web Analytics**: free, no cookies, no consent banner. It replaces Google Analytics (Site Kit) on the live WordPress site; the old Google Analytics history stays in the Google account (nothing here exports it). Creating the site in Web Analytics and copying its token is the owner's step in the dashboard ([`cutover-runbook.md`](cutover-runbook.md), P-24); the code and the tests are here, built and run locally only: **no beacon was ever delivered to Cloudflare from this repository**.

**The model: the variable plus our own tag (Cloudflare's "manual" setup), not the zone's automatic injection.** Why:

- **Explicit and testable.** The page either carries one `<script>` or it does not, and every state is a test (below). The automatic injection happens at Cloudflare's edge, on a zone, and cannot be run, seen or tested here.
- **Off wherever it should be.** Unset (local, tests, e2e, `pnpm seo:parity:local`, staging) means no script and no tag at all. Staging is on `*.workers.dev`, and the site in Web Analytics is created for the real host (Cloudflare checks the page's host against the hostname of the site, by suffix), so a beacon there would only be refused.
- **It costs no Worker request.** A manually embedded beacon reports to `cloudflareinsights.com`; the automatic setup of a proxied zone reports to the zone's own `/cdn-cgi/rum`, a path whose handling in front of this Worker nobody has seen (Cloudflare's FAQ, below). The 100,000 requests a day of the Free plan are not touched by the model chosen.
- **It works with the route over the proxied record** (D-02). The one thing to get right is that the zone's automatic injection stays OFF for the hostname (the dashboard offers "Enable with JS Snippet installation" for a proxied site): Cloudflare reads one snippet per page, and says you cannot have several.

**The tag** (the form is Cloudflare's, read from its documentation on 2026-10-15; nothing was taken from memory): one script at the end of `<body>`, after the footer, rendered by `src/components/WebAnalytics.astro` (which `src/layouts/Base.astro` includes right after `<Footer />`) and nowhere else:

```html
<script type="module" src="https://static.cloudflareinsights.com/beacon.min.js" data-cf-beacon="{&quot;token&quot;:&quot;<32 hex characters>&quot;}"></script>
```

Astro writes the JSON attribute with `&quot;`, which a browser reads back as exactly Cloudflare's `data-cf-beacon='{"token": "..."}'`. **It is `type="module"`, not `defer`** (the ticket text said `defer`): Cloudflare's FAQ now shows `type="module"` in the manual snippet, says the dashboard's installation instructions carry it and explains why (old browsers that cannot parse the script skip it), and a module script is deferred by definition, so a `defer` next to it would do nothing. A `HEAD` request for the beacon on 2026-10-15 answered `access-control-allow-origin: *`, so a module load from this site is allowed. There is no `integrity` attribute: Cloudflare does not version the file, and its FAQ says there is no safe way to pin it for a manual embed.

Sources, all read on 2026-10-15 (no account used): `https://developers.cloudflare.com/web-analytics/faq/` (the snippet, `type="module"`, hostname matching, one snippet per page, no SRI, what a Content-Security-Policy needs), `https://developers.cloudflare.com/web-analytics/get-started/` (manual setup for sites not using the automatic one) and `https://developers.cloudflare.com/speed/observatory/rum-beacon/` (what is collected, privacy, the EEA/EU option).

**One variable, `WEB_ANALYTICS_BEACON_ID`, read in two places, because the site has two kinds of page.** It holds what Cloudflare calls the site token (the `"token"` of the snippet): exactly 32 hexadecimal characters. It is **public** (it is in every page's HTML), and it is deliberately **not** named `..._TOKEN`: `cf/scripts/staging-deploy-command.mjs` refuses every name with `TOKEN` in it as a secret, and a beacon id is not worth a hole in that rule.

| | Pages | Where the value comes from | How it is set |
| --- | --- | --- | --- |
| **Build** variable | the **prerendered** pages: `/`, `/gabung-siswa`, `/program/<id>` (5 files, served by the assets layer with no Worker involved; `/donasi` was the sixth until SAKEM-105) | the **shell environment of `astro build`**, read by `astro.config.mjs` into the constant `__WEB_ANALYTICS_BEACON_ID__` | `WEB_ANALYTICS_BEACON_ID=<32 hex characters> pnpm build`, on the command line (not `export`ed: a later staging build in the same shell would take it, and staging stays clean) |
| **Worker** variable | the pages the **Worker renders**: `/blog`, an article, `/tim`, `/donasi`, `/gabung-siswa/docs`, `/kontak` and the 404 page | `env.WEB_ANALYTICS_BEACON_ID` at request time | `--var WEB_ANALYTICS_BEACON_ID:<32 hex characters>` at deploy (public per-deploy values are never in git) |

Each kind reads **only its own source**, with no fallback either way (`webAnalyticsBeaconId` in `src/lib/web-analytics.ts`): a deploy has to set both, from one value. A `--var` alone leaves the home page without a beacon, and a build variable alone leaves the blog without one; the runbook's smoke test T-25 compares a prerendered page with a rendered one, and `scripts/e2e-analytics.mjs` pins both halves. Why this shape:

- **A Worker variable cannot reach a prerendered page.** The HTML is made once, at build, and the assets layer serves it without running the Worker. Making it reach them would need `assets.run_worker_first`, which turns every view of the home page into a Worker request: not done.
- **The prerender must not read `env`.** Measured on 2026-10-15 with a probe in the layout: in the build, `import { env } from 'cloudflare:workers'` inside a prerendered page holds the **vars of `wrangler.jsonc` and the contents of `.dev.vars`** (a value written there showed up in the built HTML) and does **not** hold the shell environment of the build. A `.dev.vars` left over from local work would therefore have put its value into a production build's static HTML. The layout takes the prerendered pages' value from the explicit constant only, so the answer to "when does a prerendered page embed an id?" is: **only when the build's shell had a valid `WEB_ANALYTICS_BEACON_ID`**; `.dev.vars` never does it (`scripts/e2e-analytics.mjs` builds with a decoy id in `.dev.vars` and checks that it appears in no page and not in the deployed config). The same build also copies `.dev.vars` into `dist/server/.dev.vars`, which `wrangler dev -c dist/server/wrangler.json` loads (a local preview of that build shows the decoy on the pages the Worker renders, found when the first run of that script did); a deploy does not upload it, so it never reaches production.
- **An invalid value is ignored, never echoed.** A value that is not exactly 32 hexadecimal characters (surrounding whitespace is ignored) is nothing: no tag. The Worker says so **once per isolate, in fixed words** (`web analytics: WEB_ANALYTICS_BEACON_ID is set but is not a beacon id ...`, no value in it), and the build prints one fixed warning. No page ever contains a value that was refused.

| State | Prerendered pages | Rendered pages |
| --- | --- | --- |
| nothing set (local, tests, staging, the plain `pnpm build`) | no script, no tag | no script, no tag |
| build variable only | the tag | none |
| Worker variable only | none | the tag |
| both, the same value (the deploy of the runbook) | the tag | the tag, the same id |
| either one invalid | none for that kind; one build warning | none for that kind; one log line, no value |

**What the page does not change.** No look (one invisible script), no copy, no cookie (nothing on the Worker's side sets one), no status code, no cache header, nothing in `<head>`. **With nothing configured the HTML is byte for byte what it was**: the six prerendered files (five since SAKEM-105) were hashed before the change and again after it, and equal a build of a pristine `origin/cloudflare` made in another folder on 2026-10-15 (`tests/web-analytics-built.test.ts` and the e2e check the end of the page, which is where a difference showed up). It is a component of its own, and placed with no whitespace before it, for that reason: Astro's compiler writes the whitespace after `</body>` differently in any layout that holds a `<script>` element in its body, and keeps whitespace around an expression that renders nothing, so a tag written in the layout itself changed every page by one space (`</body> </html>` instead of `</body></html>`), harmless but not "unchanged". Nothing on the **admin or portal**: `/admin` is a 308 to the admin host, `/api` a JSON 404 and `/portal` another Worker; `cf/admin` (both SPAs and both Workers) holds no mention of the beacon, which a test scans for. Answers that are not HTML (`robots.txt`, the sitemap, redirects, the JSON 404) carry none.

**Content-Security-Policy: none is sent, so none is extended.** No page, no Worker code and no `_headers` rule sets one (see also "Service binding and Turnstile"). When one is added, with the beacon configured it must allow exactly `script-src https://static.cloudflareinsights.com/beacon.min.js` and `connect-src https://cloudflareinsights.com` (Cloudflare's FAQ names both for a manual embed; the automatic setup would need `'self'` for `connect-src` instead) and nothing more. The tag has no inline code, so no `'unsafe-inline'` is needed for it. The two origins are the constants `BEACON_SCRIPT_URL` and `BEACON_REPORT_ORIGIN` (`web-analytics.config.mjs`, pinned by a test); a test fails the day a policy header appears and says what to add.

**Privacy, for the policy page (SAKEM-056).** Cloudflare says the beacon "does not store any data in the browser or access any storage data", naming cookies, `localStorage`, `sessionStorage`, the IP address and IndexedDB; it reads the browser's performance APIs and sends page-load timings (a page load id, the referrer, the landing path, Core Web Vitals and navigation timings), and the receiving data centre discards the IP address and does not keep it in its core databases or logs. Cloudflare also says it does not log query strings. So: **no cookie, no consent banner** (D-07), and the privacy policy should say that visits are counted with Cloudflare Web Analytics, which uses no cookies. The wording is Dzul's. Two things that are not known: whether the "exclude visitors in the EEA/EU" setting (Cloudflare says Free accounts get RUM with EU traffic excluded by default, and offers it for proxied sites) applies to a manually embedded snippet; and how many visitors an ad blocker hides (Cloudflare's FAQ says such tools block the beacon, so the counts are a floor).

**Cloudflare's checks that this design meets** (FAQ): the beacon needs a `Referer` or `Origin` header to pass its CORS check; the site's `Referrer-Policy: strict-origin-when-cross-origin` sends the origin to another host, and a `POST` carries `Origin` anyway. The site registered in Web Analytics is for the hostname `sakolakembara.org`; the match is by suffix, so `www` and the other hosts of the apex pass too.

**Tests.**

- `tests/web-analytics.test.ts` (unit, no build): the id's shape (valid, 24 invalid forms, never throws), which page gets which source (prerendered: build only, never the Worker variable; rendered: Worker variable only, never the build), the log line (fixed words, once, no value), the tag attribute, the component and the layout source (one tag, guarded, module, included once right after the footer with no whitespace, not in `<head>`, one place in `src/`), nothing in `cf/admin`, no Content-Security-Policy anywhere, the declarations (`env.d.ts`, `wrangler.jsonc`, both example files, `astro.config.mjs`, `vitest.config.ts`), and the deploy-command printer (accepts the id for the site only, refuses a wrong shape without repeating it, still refuses every secret name, keeps the same shape as the site's own validation).
- `tests/web-analytics-built.test.ts` (needs `pnpm build`): the five prerendered pages of `dist/` (six before SAKEM-105) have no beacon when the build had no variable, and exactly one, with that id, when it had.
- `scripts/e2e.mjs`, group `analytics` (the plain build under `wrangler dev`): nothing carries the beacon with nothing set; with the Worker variable every rendered page has exactly one correct tag and its status, cache header and policy headers are unchanged, while the prerendered pages and the non-HTML answers have none; an invalid value is ignored, appears in no page and no log line, and is reported once.
- `scripts/e2e-analytics.mjs` (`pnpm test:e2e:analytics`, one extra `astro build` into a temporary folder, about two minutes): the build variable reaches all the prerendered pages (five; six before SAKEM-105), a decoy id in `.dev.vars` reaches none and not the deployed config, both kinds of page carry the same id when both variables are set from one value, and with the build variable only the rendered pages have none.

## SSR blog pages and the 10 ms limit

The blog was the one part of the site that cost the Worker nothing: 80 prerendered files served by the assets layer. Since SAKEM-080 part E every `/blog`, `/blog/<slug>` and `/sitemap.xml` view invokes the Worker (one request of the 100k a day) and renders there. **Nobody has measured the CPU of that on Cloudflare**; the local numbers are wall-clock through `wrangler dev` (workerd on a laptop, the fixture API on loopback) and prove nothing about Worker CPU. What is in place to keep it small:

- the API's JSON comes from `caches.default` after the first view (60 s), so a hot page costs a cache `match`, one `JSON.parse` of a payload without `contentMarkdown` (the blog stores the parsed value), and the Astro render; no fetch, no markdown, no D1 on the Worker side;
- the Worker holds no markdown engine, no article text and no metadata index (checked by a test), so the bundle stays small and a cold isolate parses little;
- images are static assets, so a list view is one Worker request, not 17;
- a probe of unknown URLs costs nothing: a slug that cannot exist is a 404 without a subrequest or cache entry, `?page=` is capped, an unknown valid slug is remembered for 30 s.

What is in place since SAKEM-091, **off unless asked for**: a copy of the rendered page in the isolate's memory (`PAGE_CACHE_SECONDS`, `src/lib/page-cache.ts`, called from `src/middleware.ts`). The staging measurement (2026-10-14) put `/blog` at 13 ms of CPU a request on a Worker with no cache, and a profile of the built Worker showed why nothing in the page's own code can fix that: more than half of a page is Astro's renderer, about a tenth is this repository's own code (the rest is the platform's Request, Response and stream objects), and the data cache above only saves the data, not the render ([`free-plan-audit.md`](free-plan-audit.md#10-cpu-on-the-hot-routes-sakem-091)). With `PAGE_CACHE_SECONDS=30` a page that depends on nothing but the API's data (`/blog?page=N`, `/blog/<slug>`, `/tim`, `/donasi`, `/gabung-siswa/docs`, `/sitemap.xml`, an allow-list) is answered from a copy for at most that long (at most 120, and never longer than the page's own `s-maxage`): the render and the API call are both skipped, and locally the Worker's own JavaScript for such a view falls by about 80%. Only a fresh 200 is copied (`s-maxage` of at least 60; `/tim` by its `x-team-source`), never a 404, a 503, a stale answer after an outage, a form or anything with a cookie; the query is reduced to what the page reads, so `?x=1` shares the copy and a visitor cannot create entries; 32 pages and 1 MiB each at most, least recently used out. A copy says `x-page-cache: hit` (the render that made it says `miss`); nothing else about the answer changes (headers and bytes are the stored ones; with the variable unset the output of every page is byte for byte what it was, compared on 15 routes). The staleness it adds is that many seconds on top of the data's own: **an admin save is not purged from it** (nothing purges any cache of this site, see [`public-api.md`](public-api.md#purge-options)), so start with 30. It is memory, not the Cache API, so it works on `workers.dev` (staging can show its effect) and is per isolate; the Cache API copy of the DATA stays as it is. What is still **not** in place: Workers Cache (it would bill static assets as requests; see the decision above). If the real CPU of an article or list view is close to 10 ms, the options in order of effort: drop `contentMarkdown` from the public article payload (the site never reads it, it is half of the JSON that is parsed on a miss), cache the rendered HTML in `caches.default` keyed by URL with a 30 s window, then prerender the 80 migrated articles again and let only the new ones be SSR. Subrequests per view are low (cache `match`, at most one fetch, at most two `put`; the Free limit is 50 Cache API and fetch calls per request); the sitemap makes about three calls per API page, so it stays under 50 up to roughly 800 articles on a cold cache.

# cf/web: the public site on Astro + Workers (SAKEM-075)

A local, thin slice of the new public site: **Astro 6 SSR on Cloudflare Workers** in front of the legacy Next app. It exists to prove the shape (SEO parity, redirects, pass-through, what runs in the Worker) before the remaining pages are ported. Context and decisions: [`README.md`](README.md).

**Status.** Built and tested locally only. Nothing is deployed, no Cloudflare account was used (`wrangler login`, `deploy` and every remote command were avoided; only `wrangler dev` in local mode and `wrangler deploy --dry-run`). **Visual QA was not done** (no browser was opened); layout, spacing and motion were not looked at, only HTML, CSS output and behaviour were checked.

## Run it

```bash
cd cf/web
pnpm install                    # its own lockfile; not a pnpm workspace
cp dev.vars.example .dev.vars   # fake local values, untracked
pnpm stub-origin                # terminal 1: stand-in for the legacy app, :4390
pnpm fixture-api                # terminal 2: content API with sample team, report and resource data, the blog from content/blog and the contact form, :4391
pnpm dev                        # terminal 3: astro dev on :4321 (the Worker runs in workerd)
```

| Command | What it does |
| --- | --- |
| `pnpm assets` | The asset pipeline (below): syncs a few root files, then makes the image ladders, the manifest and the PDFs from the root `public/`. Incremental. `dev`, `test` and `build` run it first |
| `pnpm build` | `pnpm assets`, then `dist/client` (assets) and `dist/server` (Worker), then `check-dist` (the asset guard) |
| `pnpm check:dist` | The guard alone, on an existing `dist/` (`-- --list` prints every `<img>` of the prerendered pages) |
| `pnpm check` | `astro check` (types for `.astro` and `.ts`); it only builds the image manifest, not the images |
| `pnpm test` | 641 unit tests (vitest, `pnpm assets` first); the ones that read `dist/` (`built`, `home-built`, `home-dom`, the dist audit in `assets`) need `pnpm build` first and are skipped without it |
| `pnpm test:e2e` | 295 checks against the built Worker under `wrangler dev` (local mode) with the stub origin and the fixture API |
| `pnpm measure [-- --next http://127.0.0.1:3055]` | Sizes, warm timings, and the "does the Worker run?" experiment; writes `.measure/results.json` |
| `pnpm exec wrangler deploy --dry-run --outdir <dir> -c dist/server/wrangler.json` | Bundle size, no login needed |

`BLOG_SOURCE=markdown pnpm dev` runs the blog from the root `content/blog` rendered at build time instead of the content API (no fixture server needed; see "Blog from the content API"). `E2E_PORT_OFFSET=1000 pnpm test:e2e` shifts every port the e2e stack uses, so two sessions can run it on one machine.

`astro dev` differs from production in two ways: static assets are not served before the Worker, and `_redirects` is not processed (the middleware answers the same redirect table instead). Use the built Worker (`pnpm test:e2e`, or `wrangler dev -c dist/server/wrangler.json`) to see production behaviour.

## Decisions and why

- **Design tokens are copied, not imported.** `src/styles/global.css` holds the `:root` vars, the `@theme inline` block, the base heading scale, the focus ring and `.blog-content` from `app/globals.css`. Importing the root file by path would pull in its Leaflet styles and, worse, its `@source not "../cf"` (added in commit 1), which would stop Tailwind from scanning this app's own files. `tests/tokens.test.ts` fails if a value drifts from the root file.
- **Fonts** are self-hosted with `@fontsource` (static files, Lora 400-700 and Plus Jakarta Sans 400-700, latin only, like `lib/fonts.ts`); two are preloaded. No Google Fonts request.
- **Blog content at build time: a small Vite plugin** (`plugins/blog-content.mjs`) turns `content/blog/*.md` into two virtual modules: a metadata index (read by the prerendered home page for its "Cerita & Inspirasi" strip, and by the markdown fixture) and the rendered bodies (imported only by the markdown fixture, so no article text is in a production Worker bundle; a test checks this). Since SAKEM-080 part E the articles themselves are not built from it: the pages read the content API ("Blog from the content API" below), and this plugin is the home strip, the `BLOG_SOURCE=markdown` fixture and, through `createBlogReader`, what `scripts/fixture-api.mjs` serves. The markdown is rendered with the engine react-markdown uses (remark-parse, remark-gfm, remark-rehype), the same `img` and `a` handling, and the plugin looks every image up in the asset manifest to put `srcset`, `sizes`, `width` and `height` on every `<img>`. Why not `import.meta.glob('?raw')` or `astro:content`: parsing and rendering happen once in Node, so the Worker and the workerd prerender never see a file system, and no raw markdown or parser ships in the Worker.
- **Redirects: one table, compiled to `_redirects`** (`redirects.config.mjs`). The assets layer answers `_redirects` before the Worker runs, so legacy WordPress traffic costs no Worker request and no CPU. Astro's own `redirects` option was not used: with params the adapter's generator (`@astrojs/underscore-redirects` 1.0.3) writes `/cerita/:slug  /cerita/:slug.html  301` and drops the destination and the status. The same table feeds the middleware (used by `astro dev` and as a safety net) and the tests, so there is one source.
- **Pass-through in a middleware plus a catch-all route.** Astro middleware only runs for a request that matches a route; without a catch-all (`src/pages/[...path].astro`) an unmatched multi-segment path such as `/portal/status` gets Astro's built-in 404 and never reaches the middleware (found in the first e2e run). The catch-all also resolves shortlinks (below).
- **`security.checkOrigin` is off.** Astro's origin check answers 403 to any POST/PUT/PATCH/DELETE with a form content type and no matching `Origin`, which would reject requests the legacy app accepts (server-to-server callbacks, a form posted from the LMS host). The Astro pages here have no state-changing endpoint; the contact form, when ported, validates `Origin` itself.
- **The 404 is SSR, not prerendered.** A prerendered `404.html` is a static file and the assets layer serves static files with status 200 (`/404` itself answered 200 in the first build). Cost: one small render per unknown URL.
- **One URL per page.** The middleware folds a trailing slash and `.html` with a 308 (Next does the same for the slash); the page's canonical link is the second line of defence. A prerendered page requested with a trailing slash is redirected by the assets layer with a **307**, not Next's 308 (not configurable).
- **Images.** Plain `<img>` with `width`/`height`, `srcset` and `sizes`; `loading="lazy"` except the hero photo (`loading="eager" fetchpriority="high"`). No Cloudflare Images and no runtime transform: every image is made at build time and served as a static asset. How: [Images and other static assets](#images-and-other-static-assets).
- **Program galleries** (`src/lib/gallery.ts`, SAKEM-080). The legacy `lib/gallery.ts` lists `public/images/program/galeri/<program-id>/` with `readdir` on every request, which a Worker cannot do (no file system; it would fail silently into an empty gallery). `getProgramGallery(id)` now reads the asset pipeline's manifest (`listImages`, see "Images and other static assets"): the pipeline reads the same folders at the repo root, so adding a photo is still "drop `4.jpg` in the folder, rebuild". Each photo gets the WebP ladder (480 to 1600 px, never enlarged, EXIF orientation applied) at hashed `/_img/<hash>-<width>.webp` URLs, so replacing a photo in place changes its URL (what the `?v=` suffix did on the Next app) and the files are cached as `immutable`; a derivative nothing refers to any more is deleted on the next run. The listing rules are the legacy ones: numbered files first in numeric order, then other names alphabetically; jpg, jpeg, png and webp (an avif or gif among the images **fails the build** instead of being skipped). A folder without photos, or no folder, **hides the whole "Galeri Foto" section** (no "coming soon" box). A photo sharp cannot read fails the build and names the file. **Alt text rule** (same as the legacy page): `Dokumentasi <program title> <position>`, with the position counting from 1 in display order, not the number in the file name. The images are plain `<img>` with `width`, `height`, `srcset`, `sizes` and `loading="lazy"` (the stage photo above them is the page's LCP image). This began as its own script (`build-gallery.mjs`, 480 and 960 px) and was folded into the pipeline once it existed, as that script's notes planned: one encoder, one manifest, one hash scheme, one set of headers.
- **Program photos and the share image.** The stage photo and the four activity thumbnails are imported by the page, so Astro hashes and resizes them (`astro:assets`), not the asset pipeline; moving them to `<Img>` is a follow-up (the share image would become the optimized original URL). The share image (`og:image`, `twitter:image`) is the stage photo as a 1200 px JPEG made at build time; the Next layout used the original file (up to 2.6 MB), so the URL differs but still names the same photo.
- **Security headers** that Caddy adds today (HSTS, nosniff, X-Frame-Options, Referrer-Policy, Permissions-Policy) are re-added for Worker and asset responses (`public/_headers` and the middleware); a test keeps them equal to the Caddyfile.
- **Team API contract** (`src/lib/team-types.ts`): `GET ${CONTENT_API_URL}/api/public/team` returns `{ "members": TeamMember[] }` shaped like the `team_members` row of `lib/db/schema/team-members.ts` (dates as ISO strings); a bare array is accepted. **This endpoint does not exist in the legacy app yet.** Cache: 5 min fresh, 7 days stale; on failure the stale copy is also re-served as fresh for 30 s so an outage costs one 2 s wait per 30 s, not one per request. `TEAM_CACHE_FRESH_SECONDS` tunes the fresh window.
- **Content lists: one loader (SAKEM-080 part D).** `src/lib/content-api.ts` is the only implementation of the timeout, `caches.default` and stale-if-error. `/tim` (`lib/team.ts`), `/laporan` (`lib/reports.ts`) and `/gabung-siswa/docs` (`lib/resources.ts`) each add their path, their parser and nothing else. The payloads are the contract's (`content-api.md`), parsed tolerantly: a malformed entry is dropped, a payload that is not a list is an API failure. The grouping is the root app's: `getReportsByYear` (newest year first, compared as strings, the API's order inside a year) and `getResourcesByCategory` (the five categories in their fixed order, empty ones omitted).
  - **Cache.** Fresh window **60 s** for reports and resources (the contract's `s-maxage`; `CONTENT_CACHE_FRESH_SECONDS` tunes it, the e2e uses 1 to 2 s), stale copy kept 7 days, a failed fetch re-serves the stale copy for 30 s. `/tim` keeps its 5 minutes for now (moving it to 60 s is the one constant `TEAM_FRESH_SECONDS`).
  - **Purge on admin save.** The cache keys are the API URLs themselves: `${CONTENT_API_URL}/api/public/reports` and `/resources` (fresh), and the same with `?copy=stale`. A purge deletes the fresh key from the Astro Worker's `caches.default` and the next request refetches; the stale key is only read after a failed fetch and is overwritten by the next good answer. The Cache API is per data center, so a purge from another Worker reaches one location only; how the admin reaches all of them (for example a zone purge of the page URL) is not settled here.
  - **Page headers** (`contentPageHeaders`). Fresh data: `public, max-age=0, s-maxage=60, stale-while-revalidate=300` (the contract's value; `max-age=0` so a browser never holds a copy past a save). Stale data: `s-maxage=30`. **Nothing to show** (API down on a cold cache, or `CONTENT_API_URL` unset): a **503 with `Retry-After: 30` and `no-store`**, the full page shell and a notice, so a crawler keeps what it has instead of indexing an empty list. An **empty list** is the legacy empty state, a normal 200. The two notices (`Laporan belum dapat ditampilkan`, `Dokumen belum dapat ditampilkan`) are **new copy**: the legacy pages had no such state (a database error was a 500), so they are for Dzul to review. `/tim` still answers 200 with its empty state in that case.
  - **Files.** The API's `filePath` is the link target as it is, root-relative or an absolute `https` URL; the Worker never proxies uploads. The parser refuses anything else (`javascript:`, `//host`, a backslash, control characters), and an external link of a resource must be `http(s)`. Until uploads are served from R2 these paths still reach the pass-through (`/reports` and `/resources` are in `LEGACY_PATHS`).
  - **Copy buttons.** A text snippet is a `<pre>` and a button (`data-copy-text` names the `<pre>`'s id; `aria-label` "Salin teks <title>"). The button ships `hidden` and the script un-hides it, so without JS there is no dead button (its row keeps the button's height, so un-hiding shifts nothing). The label swaps to "Tersalin" for 1.8 s (the legacy wording and timing), a visually hidden `role="status"` says so ("Teks tersalin ke papan klip."), and a refused clipboard falls back to a hidden textarea and `execCommand` (an `astro check` hint about its deprecation, like `/donasi`).
  - **Design system additions.** The report categories use the legacy Tag hues (`blue`, `green`, `purple`, `amber`, plus `red` and `gray`), added to `lib/ui.ts` with the root class strings, and eight lucide icons went into `Icon.astro` (`book-open`, `clipboard-list`, `folder-open`, `sparkles`, `users`, `external-link`, `link`, `type`).
  - **"Open Recruitment Gen 6"** is hard-coded as in the legacy page, with a comment pointing at SAKEM-059.

- **Blog from the content API (SAKEM-080 part E).** `src/lib/blog.ts` hands the pages a `BlogSource` (`list`, `article`, `all`); two implementations sit behind it. **`api`** (default, what production runs) is `src/lib/blog-source.ts`: `GET /api/public/blog?page=&pageSize=` and `/blog/{slug}` of [`content-api.md`](content-api.md) through the **same loader as the other content lists** (`src/lib/content-api.ts`: `caches.default`, **60 s fresh** with `CONTENT_CACHE_FRESH_SECONDS`, a 2 s timeout, the last good copy for 7 days, **stale-if-error**, re-served as fresh for 30 s during an outage so it costs one 2 s wait per 30 s). The blog needed three additions, all optional on `loadContent` and off for the other callers: `notFoundTtlSeconds` makes the contract's `404 {"error":"not_found"}` an answer (source `not_found`, remembered for 30 s so probing cannot hammer the API, and the stale copy is dropped so an outage after an unpublish cannot bring the article back; a 404 with any other body, such as a wrong base URL answering HTML, stays a failure, so it can never make a page look deleted); `serialize` stores the parsed value, so `contentMarkdown` (unused here, half of the payload) is not cached or parsed again; `onFailure` logs a fixed word (`status 500`, `timeout`, `invalid payload`), never a body or a URL. The page answers by what the loader returned, through `contentPageHeaders` like `/laporan`: 200 with `s-maxage=60` (fresh) or `s-maxage=30` (stale), **404** with `s-maxage=30` for `not_found`, **503** with `no-store` and `Retry-After: 30` when there is nothing to show; `x-blog-source: network|cache|stale|empty|not_found` for debugging. **`markdown`** (`BLOG_SOURCE=markdown`, read by `astro.config.mjs` and `vitest.config.ts` as the build-time constant `__BLOG_SOURCE__`) is the old behaviour, `src/lib/blog-markdown.ts` over `virtual:blog-index` and `virtual:blog-bodies`: a fixture for `pnpm dev` without the fixture API and for tests, never for a deploy. It is reached through a dynamic import behind the constant, so a production build holds no article text (`tests/built.test.ts` checks the bundle: no body and no slug of the markdown index). The pages cannot tell them apart. One implementation of the contract's rules (`featured`, paging and clamping, `pageSize` 1 to 50, `related`, the slug grammar, the page cap) is `blog-contract.mjs`, shared by the markdown adapter, the fixture API (`scripts/fixture-api.mjs`, which serves all 80 articles from `content/blog` through the same render pipeline as the build, `createBlogReader` in `plugins/blog-content.mjs`) and the tests; the old sync helpers (`getRelated`, `getBlogPage`) are thin wrappers over it. The page shows `contentHtml` **unescaped** (`set:html`): trusted only because the API sanitizes at save. Covers are looked up in the asset manifest at request time (`coverAttrs`): a migrated image gets its WebP `srcset` and the `%40` form, the width and height are the API's (`imageWidth`, `imageHeight`), any other path (an R2 upload, an external URL) is used as given. **Inline images inside `contentHtml` are used as given**: the markdown fixture's HTML has `srcset`, `width` and `height` from the manifest because the build pipeline rendered it; HTML the API's save-time renderer produces has what that renderer puts there (the seed of the 80 migrated articles should be rendered with `plugins/blog-content.mjs` to keep their responsive images). A slug outside `^[a-z0-9][a-z0-9_-]{0,199}$` is a 404 without asking the API; `?page=` is capped at 500 before it is asked (so probing creates a bounded number of cache keys). Nothing in front of the Worker honours `s-maxage` today (the Worker runs before the zone cache); the header is the contract's value for anything that does later. **Do not turn on Workers Cache (`cache.enabled`) to speed this up: its docs bill every request, static assets included, as a Worker request, which would spend the 100k a day on images.** The sitemap is SSR too (`all()`: page 1 with `pageSize=50`, then the rest, plus `featured`, sorted newest first); with the API down and no copy it answers 503 with `Retry-After: 300` instead of a sitemap without the articles. Its `lastmod` is `modifiedISO` when a list entry carries it (the contract's entries do not), else the publication date `dateISO`; the markdown sitemap used `modifiedISO`, so an edited article may show its first date until the API adds `modifiedISO` to list entries (a backwards compatible change, parsed already). The blog reaches the API through `lib/api-client.ts`: `CONTENT_API_URL` when set (local, CI), else the `API` service binding, so unlike `/tim`, `/laporan` and `/gabung-siswa/docs` it needs no public API URL in production. The home page's "Cerita & Inspirasi" strip still reads the build-time markdown index (the home page stays prerendered and costs no Worker request): a new article shows there after the next build, not at once.
- **Contact form (SAKEM-080 part E).** `/kontak` is SSR because it receives the form. `src/lib/contact.ts` holds the fields, the rules and the Indonesian messages (the legacy ones, word for word, plus the one unavailable sentence, which is new copy); `src/lib/contact-submit.ts` does the work; `src/pages/kontak.astro` and `src/components/contact/ContactForm.astro` are the markup. **Without JavaScript**: the form posts `application/x-www-form-urlencoded` to `/kontak`; a valid post answers **303** to `/kontak?terkirim=1` (the confirmation, so a refresh does not post again), anything else renders the page again with the legacy message, the typed text put back and a status that says what happened: 400 invalid, 413 too large, **429** too many (the Worker's limit, or the API's `rate_limited`) or the same email again (`duplicate_recent`, its own legacy message), **503** the API said 503 or any 5xx or was unreachable or slow (new sentence, `Retry-After: 30`); every one of them `Cache-Control: no-store`. A filled honeypot is answered like a success and the API is never called. The only script (inline, 360 bytes raw, 245 gzip, 61 of them Vite's `globalThis.process` preamble) disables the button and shows "Mengirim..." while the post is in flight (the React form's pending state) and undoes it when the browser restores the page from its back/forward cache. Order: Origin check (same origin or absent, a courtesy: Astro's own check is off for the pass-through) -> the body is read with a 32 KiB cap -> rate limit by `CF-Connecting-IP` -> validation -> one JSON `POST /api/public/contact` to the API Worker. **Transport A of the contract**: an internal **service binding** `API` (`wrangler.jsonc`, placeholder service name `sakola-kembara-api`), no signature and no shared secret; the visitor's address travels in `X-Sakem-Client-Ip` (a client-sent value is never forwarded, only `CF-Connecting-IP` is read; when it is missing or malformed the fixed `0.0.0.0` goes, the contract's shared "unknown" bucket). Locally and in tests `CONTACT_API_URL` points at the fixture API and wins over the binding; never set it in production. **Rate limit**: `env.CONTACT_LIMITER`, a Workers rate-limit binding (5 per 60 s; its `wrangler.jsonc` block is a comment, because `namespace_id` is chosen at deploy time), else an **in-memory fixed window** per isolate (documented dev fallback: it only slows a script down, the API Worker applies the contract's exact limit behind it); a binding that throws never takes the form down. The status mapping, the validation (a hand-written equivalent of the legacy zod schema, **checked against the real zod schema on 11,088 inputs** in `tests/contact.test.ts`, so the Worker ships no validation library) and the "nothing personal is logged" rule (failures log a status and the API's error code, never a name, address, message or visitor address) are tested in `tests/contact.test.ts`; the rendered page, every status code, IP forwarding and the log are checked end to end (`scripts/e2e.mjs`, group `contact`, including a run with a real local rate-limit binding). Contact details are ported as they are (`contactInfo`), with a comment pointing at SAKEM-055 (the WhatsApp number looks like a placeholder and differs from the footer's email).
- **Home sections (SAKEM-080 part A).** Copy and data are in `src/lib/home-data.ts` (a file of its own, so parallel pages do not collide in `site.ts`); `tests/home.test.ts` compares every value with the root `lib/data.ts` (it imports it) and every phrase with the legacy components. Photos and logos are imported by the components, keyed by `id`, and resized at build time: the seven testimonial portraits went from up to 1.1 MB JPEGs to webp at 256, 384 and 640 px; the six logos to webp at 136 and 272 px; the page references 49 image files (srcset variants included), the largest 157 KB (the 1200 px hero), and no original.
- **Testimonial carousel: CSS scroll-snap, not a slider.** The track is an `overflow-x` scroll-snap row (two cards at a time from `md`, one below) in a focusable `role="region"` with `aria-roledescription="carousel"`; arrow keys, touch and trackpad scroll it with no JS. About 1 KB of script adds the previous/next buttons (they wrap around, like the Next version) and the dots; until it runs those controls are `hidden`, so there is never a dead button. `scrollTo` carries no `behavior`, so CSS decides (smooth, or instant under `prefers-reduced-motion`). Differences from the Next carousel: one card per testimonial in the HTML (Next rendered every card twice, once per slide), the last position shows cards 6 and 7 instead of 7 and 1, there is one dot fewer than cards when two are in view, and the dots have a larger invisible hit area.
- **Map: server-rendered list, Leaflet loaded lazily.** The panel is HTML first: the eight branches as a list (what crawlers, screen readers and a visitor without JS get). The map loader (an `IntersectionObserver`, `rootMargin` 400 px) dynamically imports Leaflet, its CSS and the marker CSS the first time the panel is near the viewport, draws one marker per list item (the list items carry the coordinates and the popup markup, so the script holds no copy) and then swaps the list for the map. A visit that never scrolls to the map never requests the Leaflet chunk (about 145 KB raw, 42 KB gzip). The CSS is imported with `?inline` and injected as a `<style>`: a plain CSS import in that script made Astro add a render-blocking `<link>` for all of Leaflet's CSS to the page. If the chunk cannot load, the list stays. Tiles still come from `tile.openstreetmap.org`, as before. Marker pulse keyframes are named `map-pulse`, so they cannot shadow Tailwind's `pulse`.
- **Entrance motion on the home sections is CSS only**: `.anim-reveal` (`src/styles/reveal.css`, inlined by Astro as a 349-byte `<style>`) runs a fade-up on a view timeline (`animation-timeline: view()`), staggered per card with `--i`. It sits behind `@supports (animation-timeline: view())`, so a browser without it just shows the content (nothing is hidden up front), and `prefers-reduced-motion` switches it off. It is not the 0.6 s time-based reveal of framer-motion; whether it feels right is a visual check nobody has done.
- **Tests that run the real scripts.** `tests/home-dom.test.ts` loads the built `index.html` into happy-dom (a dev dependency) and runs the page's actual scripts: it opens the dialog, drives the carousel (geometry stubbed, there is no layout), runs the lazy map (Leaflet really loads and draws the eight markers and a popup) and checks that nothing logs a console error. It proves the markup and the scripts agree; it is not a browser.

## Images and other static assets

Every image and file is a **static asset** (free and unlimited; anything that goes through the Worker counts against 100k requests per day). The root `public/` is the single source and is never modified; everything below is generated into gitignored folders of `cf/web` by `scripts/build-assets.mjs`, which `pnpm dev`, `pnpm test` and `pnpm build` run first. Numbers and settings live in `assets.config.mjs` (pure, shared by the script, the blog plugin, `src/lib/images.ts` and the guards).

**What it makes, for every `jpg`, `jpeg`, `png` and `webp` under `public/images/**` and `public/blog/images/**` (273 files):**

| Output | Path | What |
| --- | --- | --- |
| WebP ladder | `public/_img/<hash>-<width>.webp` | 480 / 768 / 1200 / 1600 px wide, never upscaled; a rung within 10% of the top one is skipped, the top is the source width capped at 1600; quality 80; PNG sources take a lossless WebP when it is at most 1.5x the lossy one (logos, screenshots, infographics, the QRIS); metadata dropped; EXIF rotation applied. 614 files for 273 images (identical sources share their derivatives) |
| Original URL | `public/<same path>` | An optimized file **in the format the extension says**, at most 1600 px wide, metadata (EXIF, GPS) stripped: JPEG mozjpeg q82; PNG lossless, palette-quantized only when it is still above 1 MiB; so `/blog/images/2025/10/1.png`, `/wp-content/uploads/...` redirects, old links and `og:image` keep working. A few migrated files are PNG data named `.jpg` (two testimonial photos) or WebP named `.png` (one partner logo): they are served as what the extension says |
| Manifest | `src/generated/image-manifest.json` | `{ "<url path>": { width, height, hash, variants: [{ width, height }] } }`, typed by `src/lib/images.ts` (`findImage`, `getImage`, `imgAttrs`, `listImages` for gallery folders). `width`/`height` are the size of the file at the original URL (the largest rung) |
| Files | `public/files/**` | Copied; a PDF above 20 MiB is recompressed (next section) |

**File names.** `<hash>` is 12 hex characters of SHA-256 over the source bytes, the encoder settings and `PIPELINE_VERSION`, so a name changes if and only if the bytes it points at change: that is what makes `max-age=31536000, immutable` safe. The same content under two paths shares one derivative. Original URLs cannot carry a hash (they must stay), so they get a day of cache instead.

**Incremental.** The manifest is a pure function of the sources and is rewritten only when it changes. A derivative is skipped when its file exists (the name is the hash); an original-URL file when `.asset-state.json` (gitignored) holds the same hash and format for it; files are written to a temp name and renamed, so a killed run never leaves a half file that looks fresh; stale files in the generated folders are removed. **Change an encoder setting in `assets.config.mjs` and bump `PIPELINE_VERSION`** so every hash changes. Cold run on this machine: 36 s for everything (full `pnpm build` 42 s); warm: 0.1 s (full `pnpm build` about 5.5 s).

**Using an image.**

1. Put the file in the root `public/images/...` (site) or `public/blog/images/...` (blog), like before; the URL path is the path below `public/`.
2. `pnpm assets` (or just `pnpm dev` / `pnpm build`).
3. In a component: `<Img src="/images/program/mentoring.jpg" alt="..." sizes="(min-width: 1024px) 380px, 100vw" />` (`src/components/Img.astro`: plain `<img>` with `src`, `srcset`, `sizes`, `width`, `height`, lazy by default; the LCP image passes `loading="eager" fetchpriority="high"`). An unknown path **fails the build**. `sizes` is the layout width of the image: the 1200 px page container is 1152 px of content, 800 px for reading width; check the real grid (`(min-width: 1024px) 380px` is the three program cards).
4. In a blog article nothing changes: `![](/blog/images/...)` in the markdown gets `srcset`, `sizes`, `width` and `height` from the same manifest; covers carry `imageSrcset` in the metadata.
5. Budgets: keep each source reasonable (the pipeline caps at 1600 px and every generated image is asserted under 1 MiB), do not add thousands of files (the Workers limit is 20,000 per version; the build fails above 10,000), and avoid characters other than letters, digits, `/ . _ -` in names: a literal `@` (five existing blog images) is answered by the assets layer with a **307** to the `%40` form, so markup carries `%40` (`assetUrl`) and the guard flags a literal `@`; the tests fail on any other character.

**Other image paths in the tree today.** A few components still import an image (`import photo from '@root/public/...'`), which makes Astro hash and resize it into `/_astro/` (`astro:assets`): the logos in the navbar and footer, the partner logos and testimonial portraits of the home page, the program page's stage and activity photos, and the QRIS on `/donasi`. They work and are not wrong; the QRIS stays an import on purpose, because its download link must be the original bytes. Everything new should use `<Img>` or the manifest so there is one system; moving those over is a follow-up (each touches a page or component of its own and its tests).

### Large PDFs

`pitchdeck-sakola-kembara.pdf` (29.1 MiB) and `kurikulum-khusus-sakola-kembara.pdf` (27.7 MiB) are above the 25 MiB per-asset limit. Ghostscript and qpdf are not installed on this machine and nothing was installed; `scripts/lib/pdf-shrink.mjs` does it with `pdf-lib` and `sharp` (devDependencies, no system tool, so it also runs in any CI): the four large RGB JPEG images of each deck (two 4200x2364, one 3000x1688, one 908x1210) are re-encoded **at the same pixel size** with mozjpeg q90 and 4:4:4 chroma, and the file is rewritten with object streams. Nothing is downscaled and no text, font or page is touched. Result: **23.2 MiB and 23.1 MiB**, the same public URLs (`/files/<name>.pdf`), generated copies in `cf/web/public/files/` (the originals in the root `public/files/` are never touched). The address bar changes after the redirect, links and search results keep working. R2 reads and the egress are free within the Free tier. The alternative that keeps the URL (a Worker route that streams `env.FILES.get(key)`) makes every download a Worker request, so it is not the default.

## Pass-through

How it works: the middleware (`src/middleware.ts`) checks the redirect table, then `src/lib/legacy-paths.ts`, and forwards with `src/lib/legacy-proxy.ts`. The request goes out with its method, headers (cookies and `Authorization` included), query and body stream; **redirects are not followed** (a 307 to `/login` reaches the browser); hop-by-hop headers are dropped; several `Set-Cookie` headers survive as several. In production (Workers **routes** mode, route covering the whole site) `fetch()` of the same URL reaches the origin behind the same hostname, so `LEGACY_ORIGIN_URL` stays unset. Locally it points at `scripts/stub-origin.mjs`, which echoes what it received.

**Proven locally** (e2e, 26 pass-through checks): GET/POST/PUT/PATCH/DELETE/HEAD reach the stub with method, query, body (also a 1 MB body), custom headers and cookies intact; two `Set-Cookie` arrive as two; the origin's 307 is not followed; `te` and `proxy-authorization` are not forwarded; the stub's `Cache-Control` survives; Astro paths (`/`, `/blog`, `/tim`, the 404s, redirects) never reach the stub. **Not provable locally:** route-mode semantics (below).

### Conflicts and findings

- **Shortlinks.** `sakolakembara.org/<slug>` is resolved by Next's root `[slug]` route against Postgres. Without care the Worker would answer those with a 404. The catch-all forwards a single segment that fits the slug grammar (same regex and 64-character limit as `validateSlug`) to the origin, which redirects (307) or answers its own 404; anything else is a 404 from the Worker without a database round trip. Static pages win over the catch-all, like in Next.
- **Files both sides serve.** The Worker ships copies of `favicon.ico`, `icon.png`, `apple-icon.png`, `og-default.jpg` and `images/logo-sakola-kembara.png` (copied from the root at build time, gitignored, so the root stays the single source). The assets layer answers first, so the origin's identical files are shadowed. `/robots.txt`, `/sitemap.xml`, `/blog`, `/blog/<slug>`, `/program/<id>` and `/donasi` are also Astro's now; the origin's versions become unreachable. Every image and PDF in the repo (blog, program galleries, hero, partners, QRIS...) is served from the assets layer too, so the origin's copies are shadowed (see "Images and other static assets"). `/_astro/*` (this app) and `/_next/*` (legacy) do not overlap.
- **Every pass-through is a Worker request** (100k per day on Free), including each `/_next` chunk, each `/blog/images/*` photo and each `/api/*` call. A `/blog` list view with 16 cover images is about 17 Worker requests. The navbar script keeps its two API answers in `sessionStorage` (announcement 5 min, signed-in session 5 min, signed-out session 30 s), so a visit costs two requests once per session, not per page. The 235 blog images (69 MB) and the other repo images and PDFs are now static assets (free, unlimited), so a `/blog` list view costs one Worker request (the page itself); e2e checks that no image or PDF request reaches the origin.
- **Blog content source of truth.** *Settled by SAKEM-080 part E:* the blog is managed in the new admin (D1, HTML rendered at save time) and the site reads it from the content API at request time. `content/blog/*.md` stays the seed of the 80 migrated articles and the markdown fixture; the legacy `/admin/blog` is not read by anything here.
- **Client IP.** The legacy rate limiter prefers `CF-Connecting-IP`. The proxy forwards all request headers; whether Cloudflare keeps that header on a Worker's subrequest to the origin needs a check on a real zone. For the contact form the Astro Worker reads `CF-Connecting-IP` itself and passes it to the API Worker in `X-Sakem-Client-Ip` over the service binding (see "Contact form"); whether `CF-Connecting-IP` also survives a service-binding call is the contract's open check.
- **Server actions** post to the page URL (`/login`, `/portal/daftar`): the e2e posts with a `next-action` header and a body, and it reaches the stub unchanged.
- `/blog/page/N?utm=x` loses the incoming query (`_redirects` keeps the destination's own query only). Not worth a code path.

## SSR blog pages and the 10 ms limit

The blog was the one part of the site that cost the Worker nothing: 80 prerendered files served by the assets layer. Since SAKEM-080 part E every `/blog`, `/blog/<slug>` and `/sitemap.xml` view invokes the Worker (one request of the 100k a day) and renders there. **Nobody has measured the CPU of that on Cloudflare**; the local numbers are wall-clock through `wrangler dev` (workerd on a laptop, the fixture API on loopback) and prove nothing about Worker CPU. What is in place to keep it small:

- the API's JSON comes from `caches.default` after the first view (60 s), so a hot page costs a cache `match`, one `JSON.parse` of a payload without `contentMarkdown` (the blog stores the parsed value), and the Astro render; no fetch, no markdown, no D1 on the Worker side;
- the Worker holds no markdown engine, no article text and no metadata index (checked by a test), so the bundle stays small and a cold isolate parses little;
- images are static assets, so a list view is one Worker request, not 17;
- a probe of unknown URLs costs nothing: a slug that cannot exist is a 404 without a subrequest or cache entry, `?page=` is capped, an unknown valid slug is remembered for 30 s.

What is **not** in place: a page-level HTML cache (the render still runs on every view; adding one on top of the data cache would stack the 60 s windows, and a stale-if-error HTML copy needs its own handling), and Workers Cache (it would bill static assets as requests; see the decision above). If the real CPU of an article or list view is close to 10 ms, the options in order of effort: drop `contentMarkdown` from the public article payload (the site never reads it, it is half of the JSON that is parsed on a miss), cache the rendered HTML in `caches.default` keyed by URL with a 30 s window, then prerender the 80 migrated articles again and let only the new ones be SSR. Subrequests per view are low (cache `match`, at most one fetch, at most two `put`; the Free limit is 50 Cache API and fetch calls per request); the sitemap makes about three calls per API page, so it stays under 50 up to roughly 800 articles on a cold cache.
